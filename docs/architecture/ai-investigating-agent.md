# AI investigating agent

ROMULUS can run a bounded AI investigation after its deterministic hunt stages finish. The agent reads the persisted hunt dossier, proposes investigation hypotheses, uses typed read and pivot tools, and writes separately labelled notes, links, rule requests, and findings. It cannot remove or change deterministic findings, lanes, coverage, incidents, or rule outcomes.

## Run flow

The hunt manifest records whether the agent was requested and which provider configuration was used. Provider readiness is checked without blocking the deterministic hunt. An unrequested, unavailable, or failed agent phase is recorded as skipped or partial and receives a deterministic template assessment.

Detection completion is recorded before agent work begins. The agent holds a separate renewable lease, including during blocking model calls. Its work cannot change detection execution state, and a live agent lease prevents deletion and maintenance. After agent work, one transaction refreshes the result from deterministic findings, records the agent's terminal state, and releases its lease. A crashed worker's persisted work can be resumed after lease expiry.

Assessment-only recovery closes a crashed investigation's running sessions under the newly claimed lease, records the interruption, and leaves the investigation partial even when the new assessment succeeds. The session cleanup and recovery audit commit together. A pending agent-off or unavailable-provider handoff can finish its template locally without contacting telemetry sources. Ready investigations still perform source preflight before resuming.

An orient session receives the system instructions and the first dossier page. It can open a bounded set of hypotheses. When there are reportable findings but no hypotheses were opened, the controller creates low-confidence hypotheses from the top finding in each incident.

The scheduler investigates open hypotheses in breadth-first rounds, with bounded concurrency and a per-hypothesis session limit. Each session starts a fresh conversation with the hypothesis card and a bounded set of earlier session summaries. Hypothesis updates and cites are persisted as events. The session stores its state, tool-call count, summary, and model calls so the phase can be resumed without rerunning a completed deterministic hunt.

After investigation, a schema-constrained assessment summarizes cited observations, inferences, hypotheses, gaps, alternatives, and next checks. The reply is validated against exactly the schema the model was given. A deterministic checker then removes uncited or unknown-alias sentences, downgrades observations supported only by AI or inferred links, blocks absence claims outside gaps and next checks, applies the stored bounds (sentence length, citations per sentence, sentences per section, each stated in the schema's descriptions), counts every sentence it drops or trims, and stores real identifiers in the report body. A reply that fails validation is retried once, with the failing fields named. A template based on the deterministic incident narrative and coverage gaps is used when no valid model assessment exists. A previous AI assessment is retained if a later attempt fails, and is labelled stale when investigation has changed since it was written.

## Admission and limits

All model actions use typed arguments. Each tool advertises the JSON schema of exactly the arguments its validator accepts: required and optional fields, defaults, bounds, patterns and enums, with descriptions for the rules a schema cannot state (which alias kind a field takes, registered rules, ATT&CK technique IDs, ordered windows). The tools that write (hypotheses, proposals, notes, rule requests and the session's end) ask the provider to enforce their shape where it can; read and pivot tools are validated by the product alone. A provider's strict mode can enforce only part of a schema and limits how much may be strict in one request, so the Claude adapter sends strict tools in a reduced form that states the other bounds in words, keeps within the documented limits and a conservative grammar budget, and sends the rest loose. Every call's arguments are validated by the product either way. When the session's wrap-up `finish_session` call is refused, the model gets one corrected attempt. Aliases are hunt-scoped, typed, and accepted only after they have appeared in trusted structured fields of the current session's prompt or a tool result. The claim checker restricts the claim kinds that each typed event family can support. Agent findings can be high or lead, and mention-only claims are lead. A duplicate proposal becomes a note only when the existing reportable finding has at least the admitted lane's strength. Duplicate checks stream matching candidates in bounded batches. Every output tool has a per-hunt cap; cap hits are recorded in the agent run. A refused tool call records why on its row as field paths and error types only (for example `summary: string_too_short` or `cites[]: alias_not_issued`), never the argument values, which can hold telemetry or model text; an assessment answer that fails validation records the same on its model-call row, the checker's drops as counts, and the triage pass its dropped items by field and reason. The agent's audit summary and the web panel show the refusals as counts by tool and reason.

Telemetry appears only in JSON data fields returned by tools. The system prompt treats it as untrusted input, and the provider port redacts outgoing text. The model cannot submit shell commands, paths, URLs, index names outside the hunt's own sources, or SQL. Its only free-form source queries go through `query_source` (below), which the hunt layer validates against allowlists, wraps in the hunt window and bounds before anything is sent.

Besides the fixed pivots (entity timeline, authentication activity, process tree, IDS alerts, deterministic links), the agent can ask a typed search, `search_events`: from a cited finding, which records in a window inside the hunt window hold given values in typed fields. It names a scope (`host`: endpoint and host logs; `network`: network logs and session records; `all`) that code maps to the hunt's targets by their role, and one to four conditions, each a typed field of the target's field contract, an operation (`eq`, `in`, `prefix`, `cidr`, `gte`, `lt`) and up to 20 values of at most 256 characters. At least one condition must be `eq`, `in`, `prefix` or `cidr`; `contains` (a retrieval aid only), `not_in`, `missing` and `exists` are not offered. Each value is parsed by its field's native type (an address, network, number, time with its offset, or boolean) and is otherwise sent exactly as written, as the value of a term, terms, prefix or range clause (or the compiler's escaped case-insensitive form for the few fields that have one); the planned query is compiled before anything is sent, and one holding any other clause type (a phrase or query-string query among them) is never sent, so a text value longer than its field's exact keyword copy keeps is not evaluated rather than matched inside longer text. A target whose contract cannot take every condition is listed as not evaluated, naming the field and operation; when no target can, the search is refused with the searchable fields that resemble each condition's, and `list_search_fields` lists the whole typed vocabulary up front. Searches run through the same partitioned, capped pivot executor and the hunt's agent source-query budget, with a smaller per-query record cap, fewer time partitions, and a per-search record bound past which the remaining targets are listed as not evaluated. Records no normalizer reads make the search partial rather than vanishing. Packet captures behind Arkime session records are never searched and are named as such. A search finds what is there; it never asserts an absence. Normalizers derive many typed values from what is stored (case folded, a canonical `sid:`/`name:` account form, a Windows host's short name, values parsed from a record's text), so zero hits is always `unresolved`, stated as no records matching in the sources searched, with the per-target coverage, the sources not searched and the caveats that say what the search could not see. An `in` on a field the compiler matches by a special equality form (a name without case, a Windows host by its short name, an account by its short name) sends that form for each value, a prefix on such a field is refused, and each hit on such a field is re-checked on the event's typed value with the compiler's own semantics: rows that value refutes are counted as discarded, and an event without the typed field is kept. Every other condition is the source's exact term, terms, prefix or range on the stored field and is not re-checked. Contracts carry each keyword field's `ignore_above` from the mapping (counted in UTF-16 code units, as Elasticsearch counts it; a flattened field's leaves take their root's): an equality value past the limit is not evaluated, and a prefix on a limited or unknown-limit field names what it cannot see. Host targets whose records can carry typed fields only in their text, and network targets holding unparsed Suricata EVE lines, get a coverage cell saying so. A source not searched makes the result, its coverage and its reach link partial. A search is refused before any query when the session's stored results leave too few page items for its bounded result, and a failed search, or one whose result could not be stored, is stored as a failure so that a repeat does not spend again. A repeated identical search in a session returns its stored result without querying again. Search reach is recorded as an agent-hypothesis link on the anchor, which never joins incidents.

`list_search_fields` tells the agent what it can search on, without any source query: the typed fields `search_events` can name (from the hunt's field contracts, with the operations the planner allows, the scopes whose sources map each field, and how many sources take each operation), the hunt's sources, and one source's own fields (mapped type, keyword-like or analyzed text, indexed, aggregatable and `ignore_above`, from its stored profile; for an Arkime viewer, the expression fields read from its field list when the hunt was profiled). A source's field names (which a dynamic mapping can take from telemetry) are shown only when they match a strict name pattern of at most 256 characters; the rest are counted, never echoed. Every listing is sorted, paged by entry count and bytes, and counted by name group, and the tool's definition is fixed text, so the tool definitions stay the same across a hunt's sessions and the prompt cache holds.

`query_source` lets the agent write its own query of one hunt source, from a cited finding, for questions typed fields cannot ask: a Query DSL query with optional aggregations, sort and size for an index, or an expression for an Arkime viewer. The source is one name from the hunt's own source table, looked up exactly. Only allowlisted query clauses and aggregation types are accepted, each with its own keys, and every capped number must be a JSON integer; anything that runs code, reads another index or reads outside the query (scripts, runtime fields, percolation, wrapped queries, terms lookups, global and join aggregations, significant-terms background counts, empty-bucket term lists) is refused at any depth before any source query. Lucene's own safety limits stay in force, since a pattern's automaton is built on each data node before any timeout applies: `max_determinized_states` is never accepted, expansion counts are at most 100, rewrites are constant-score only, and a regular expression, wildcard pattern, terms include or exclude, or query string holding a regular expression is at most 1,000 characters; an Arkime expression holds at most two regular expressions of at most 200 characters. Field names and labels must match a strict name pattern; every structural and option key is also checked against a list of forbidden constructs. A top-N aggregation with other values left out, and a source's own time gaps, make the answer partial. ROMULUS builds the body itself: the agent's query is one `bool.filter` clause beside the hunt window's range on the source's time field (a window outside the hunt's is clamped), with fixed size (at most 100 rows), timeout, terminate_after and total-count caps, and aggregations bounded by their sizes, their depth, the product of their bucket counts and the documents their top hits return. It goes through the existing client and request allowlist as `POST /<index>/_search`; an Arkime expression goes to the viewer's `GET /api/sessions` for at most 100 session ids, which are then read from the hunt's session index inside the window. Each query spends the agent's source-query budget and shares, and a repeat spends nothing. A query the source rejects (HTTP 400: a parse error, an unknown field) is returned as the source's bounded, redacted error text so the agent can correct it, and is never sent again; other failures and timeouts are unresolved. Returned records a normalizer reads are stored as evidence the agent can cite and pass through direct detection; the rows and aggregations are kept as a bounded, redacted preview, and aggregations are not citable. Zero hits is always `unresolved`, and rows past the size, timeouts, early stops and cut buckets are named.

A preview row that no normalizer reads is kept as a raw record (`romulus.evidence.raw_citation`, table `agent_raw_record`) with its own alias kind, `Q`, so the agent can cite it the way an analyst cites a log line. A raw record keeps its source reference (index and record id, or the Arkime session read from the session index), its time when the source's time field holds one, the cleaned and redacted record as JSON text cut at 16 KB and marked when cut, the digest of the record as the source returned it, whether it holds instruction-shaped text, and its provenance (agent session, task and request digest, and the redacted query). One row is kept per hunt and source record, so a record returned again keeps its row and alias. At most `AGENT_MAX_RAW_RECORDS` rows are kept per hunt (default 1,000); past the cap a row is not kept, the query result names how many were not, and the report counts them. Only the preview's rows (at most 20 per query) are candidates, never every returned row. Nothing is extracted from a raw record: it has no typed fields, no entities and no detection rule runs on it, and every view labels it "raw record, not normalized". It shows that a record with this text exists, never that an action happened. So an AI finding that cites only raw records must be a `mention` claim, which is capped at lead with low confidence and stays an agent finding; a finding that also cites typed evidence keeps the claim its typed events support and notes the raw corroboration. A finding citing only raw records takes no ATT&CK techniques, and is dated by its raw records' times only when it cites no typed event. Raw record ids are kept in the finding's admission gates, never among its typed event ids. Hypotheses, links, notes and rule requests may cite raw records too, but a hypothesis is marked supported or refuted only with at least one cite in that role that is not a raw record. A raw record's time is read with its target's clock (epoch seconds for Zeek, milliseconds for a numeric date, an RFC 3339 time with its offset) and kept only inside the hunt window; otherwise its text is shown as unparsed. The report's raw-record index carries the text of the first 200 cited records and the reference and digest of the rest. In the assessment, a sentence that cites only raw records is never `observed`, and the narrative's grounding counts a raw record as observed text: it is never strong (citing one never lifts a paragraph out of Context) and never benign, and a paragraph citing only raw records is weakly supported with its own reason. `search_events` counts the matched records no normalizer reads and keeps the first 20 of them as raw records in the same way; the agent reads their text with `get_evidence`.

Budgets bound calls, tokens, wall time, and optionally cost. The token budgets count budget tokens, weighted by price: on the anthropic provider a prompt token read from the prompt cache counts `AGENT_CACHE_READ_TOKEN_WEIGHT` (by default 0.1) and one written to it `AGENT_CACHE_WRITE_TOKEN_WEIGHT` (by default 1.25) of an uncached one, output tokens count once, and every other provider counts each token once. The weights are recorded with the hunt's budgets, every call row records its budget tokens beside the raw counts, and the worst case checked before a call counts its whole prompt at the dearest weight. The controller preserves an assessment reserve during investigation, records billed provider failures, and checks remaining budget before retry attempts. An agent limit or provider failure affects the agent phase only.

Every limit is the hunt's own. It is pinned in the manifest when the hunt is created (a quick, standard or deep profile plus optional per-limit values), and an analyst's budget extensions add to it. The agent never reads the live settings for it (see ARCHITECTURE.md, "Hunt controls").
- A running phase picks up raised call, token, time and cost limits at its next model call, and raised source-query shares at its next session.
- A run that ended partial on a limit continues, once budget is added, from its persisted hypotheses, sessions and spend.
- A continued run does not start again. Orient runs only when no orient session finished and none stored hypotheses (it never ran, or was interrupted first); otherwise the run goes straight to the open hypotheses, in the usual order and session limits, and assesses once at its end. It assesses only when it asked the model something: when the budget left cannot fit one investigation call beside the assessment's hold, it says so (`no_new_investigation`) and the stored assessment stands. A hypothesis's session counts toward its limit only once it makes a model call.
- The assessment's hold is the reserve fraction of what the run had left when it began (at least one assessment call's worst case), so an extension is not swallowed by a hold sized on the whole budget.
- Orient, every session of it together, may spend at most 40 % of the token budget (`cap:orient_token_share`). Its calls carry the dossier and are the largest the agent makes; without the share, a quick budget could be spent re-reading findings before any hypothesis is investigated. With the 15 % assessment hold, investigation keeps at least about 45 %.
- Each continuation is audited (`hunt.agent_resume`: who, why — extension, stop cleared, interrupted — and the starting phase), and the Run tab lists every run's end reason and continuation, so a stop's reason survives the run that follows it.
- An analyst's stop request is checked before every model call, every read tool call and every round. Once it is set, no further model call starts (no triage pass and no assessment). The run keeps what it stored, ends `partial` with `stopped_by_analyst`, and a resume continues it.

The agent's pivots share one hunt total of source queries, `AGENT_MAX_SOURCE_QUERIES` (by default 2,000: each query is a read-only, bounded request, and the agent is bounded apart from it by calls, tokens and wall clock). Every query is reserved atomically and recorded in the audit with its session and purpose, so a resumed hunt continues from what was spent. The total is shared out so that no session or call starves the rest: all orient sessions together take at most 20 % of it; an investigate session takes what remains divided by the open hypotheses that can still be given a session, its own included; and one tool call spends at most 10 % of its session's share, never less than 32 and never less than one query for each source the call plans, and never more than what the share has left. Each share is set when its session starts, from the spend persisted so far, so what a session leaves unused flows to the sessions after it. Within a call, each planned source gets the queries left divided by the sources still to search. When what is left cannot give every planned source one query, the call starts at a source set by the hunt's persisted spend, so successive calls and sessions reach the sources an earlier call left unsearched. The assessment reads no source, so nothing is held back for it. A cap that stops a pivot names itself: `agent_source_query_budget:<n>` (the hunt total), `agent_session_source_query_share:<n>`, `agent_call_source_query_slice:<n>` or `agent_call_source_share:<n>` (one source's part of its call), in the result, its unresolved coverage cells and an `agent.source_query_cap` audit record. Each cap reached is also one of the agent run's limits (`cap:source_queries:<cap>`), so its summary, the assessment's input and the report say the investigation was budget-limited. When nothing is left to spend, the pivot creates no task and returns one failed result naming each planned source as not searched; a pivot whose every searched cell failed is failed, not partial. A cap is never zero hits or an absence. A search does not list the packet captures behind an Arkime session index as not searched when every packet behind the index (its earliest first packet to its latest last packet, as profiled when the hunt started from a complete inventory) is outside the search window; it counts them in one summary line instead, and an index whose span is unknown stays listed.

Candidate citations have a transactional event index for duplicate checks and evidence lookups. Inserts and citation replacements maintain it in the same transaction; upgrades backfill existing candidates in bounded keyset batches. Incident construction projects only the stored provenance, ATT&CK and subject/context citation inputs it needs, preserving deterministic incident membership without loading full candidate rows.

## Reports

The manifest exposes agent provenance, usage, hypotheses, output counts, notes, rule requests, limits, and unworked hypotheses. Agent findings carry `provenance: "agent"`; agent links are displayed as hypotheses and do not join incidents. The Markdown report starts with the assessment and labels it as AI-generated and unconfirmed. The cross-hunt canonical projection keeps agent-only content in its `ai` section so it cannot alter deterministic comparisons.

Detection results and lane totals count deterministic findings, including genuine rule matches discovered by agent pivots. Agent-proposed findings are counted separately and labelled unconfirmed.

The CLI offers `hunt start --agent` and `hunt start --no-agent` (with `--effort` and `--agent-max-*` for the hunt's agent budget), `hunt extend` to add budget, `hunt stop --agent-only` to stop only the agent, `hunt resume --agent-only` to continue only the agent, plus `agent reassess` to create another assessment revision and report revision. `--agent-model <id>` on `hunt start`, `hunt resume` and `doctor` replaces the configured model for that run only, and the manifest and agent run record the model used. A resume whose model differs from the one the hunt's agent recorded is refused unless `--force-model` is given; a forced resume records a `hunt.agent_model_forced` audit event with the old and new model, and the manifest's agent provenance lists those switches. The triage pass runs on its own model, `AGENT_TRIAGE_MODEL` (empty means `AGENT_MODEL`), on the same provider; `romulus triage --agent-model <id>` replaces it for that run only, and the triage summary and prompt digest record the model used. `doctor` checks the triage model too when it differs from the agent's.

The executive DOCX includes the same assessment header, sentences, citation labels and checker explanation as the manifest. Agent text is plain text in Word, including strings that resemble links or field instructions. Historical reports without an assessment retain their original rendering.

## AI triage order

After the agent phase ends, when the agent was requested and its provider is ready, a separate triage pass proposes which finding groups an analyst should review first. `romulus triage <hunt>` runs it on any finished hunt; `--export <file>` writes the resulting order as JSON (every surfaced finding id, in triage order) for evaluation. The pass claims the agent lease and always releases it without changing the agent's state; a hunt with no agent record is left with none, and an interrupted pass leaves only a terminal placeholder that every reader treats as no agent record and that is never resumed as an agent phase. `AGENT_TRIAGE=off` disables the automatic pass.

The deterministic report order stays authoritative. Triage changes no lane, rank, Reported flag, entity score, candidate, citation or report order: it is stored in its own table and rendered as its own labelled section, "AI triage order (model-proposed; the deterministic order is authoritative)", after the deterministic findings in the Markdown report, and on its own web page.

- **Groups, not the top of the ranking.** Every surfaced finding (urgent, high and lead lanes) is placed in a group: one rule on one primary target (the finding's listed entity from the final ranking, else its first typed host, service, address or account) within one report section. The model reads one card per group: rule and title, lanes, ATT&CK tactics, finding count, distinct entities with counts, time span, best deterministic position and up to three claim excerpts. Findings the AI agent proposed form their own groups and are never sent or promoted.
- **Untrusted card text.** Claims, entity names and every other telemetry-derived string are length-capped, carried as escaped JSON between data markers that the data cannot forge, and flagged when instruction-shaped. The system prompt treats them as data.
- **Validated output.** The model answers each card with a group id, an assessment (`likely_attack`, `possible_attack`, `likely_benign`, `insufficient_evidence`), an optional incident label clustering groups it believes belong together, a short rationale and up to eight finding ids cited from that card. Each item is checked on its own; an unknown or repeated group, a bad assessment, an over-long or malformed field or a citation from another group drops that item, counted by reason.
- **Promote-only, bounded in findings.** Within each report section at most `AGENT_TRIAGE_PROMOTE_PER_LANE` groups (default 10) assessed as likely or possible attack are promoted: all likely-attack groups before possible-attack ones, and within each the most buried first (the largest best deterministic position, ties by group number), because triage exists to surface what the deterministic order buried; neither chunk order nor the model's own ordering decides. A promoted group moves ahead only the findings the model cited for it, its evidence (cites are checked to be among its claim excerpts, at most three), group by group in that selection order; a promoted group that cited nothing moves nothing and is listed as "promoted, nothing cited". The rest of each group and every other finding keep their deterministic relative order. Placement happens after the model answers, so it is outside the prompt digest; its version is recorded with each pass and in the export header, and a pass placed under another version is stale. No finding moves down by more than promote-per-lane x 3 findings (30 by default), and none is removed. The view lists each promoted group's moved findings and how many more stay in their deterministic place.
- **Budgets and honest partials.** Calls, prompt tokens, output tokens and wall time have their own settings; each call is checked first against its worst case, including the provider's thinking allowance. Cards are sent in chunks sized to one call's input and output room. A budget hit, a provider failure, a refusal or invalid output leaves the untriaged groups in deterministic order, and the view says how many groups were triaged and why the others were not. Triage calls are recorded as model calls and never spend the agent's budget.
- **Bounded and deterministic.** The deterministic order, groups and cards are staged in a temporary database under the stage directory, held to the site's stage byte budget and volume reserve (a refusal is a recorded failure that keeps the deterministic order), so memory is bounded by one page of findings and one card whatever the hunt's size. Cards are built once, for the digest and the calls. The view's rows are finished in the stage before publication, so the shared database's write transaction only inserts them. The pass's prompt digest covers the prompt, schema, grouping, provider, model, settings and every card: the same input gives the same order, and a completed pass with the same digest is not run again unless forced. The wall budget counts staging, and `AGENT_MAX_COST_USD` with the agent's prices caps each pass's cost when set. The report marks the view stale when the hunt's deterministic order no longer matches the pass's: it checks the finding count and final ranking, then digests the findings it already holds by the same order key the pass staged them by, without staging anything; a check that cannot run leaves the view unverified and never blocks the report. The web page uses the count and ranking checks. `romulus triage --export` re-stages the order, refuses a stale pass unless `--allow-stale`, and names the latest failed attempt. The stage keeps SQLite's temporary structures in memory and needs no large one: every index exists before its table is filled, and the order and groups are read through them. Findings an investigator case discovered stay in their groups and are counted on the card and in the view.

## Analyst views

The new-hunt form shows provider readiness and the configured model. Its agent checkbox follows the default only when the provider is ready, and any remote-egress banner appears before submission. The hunt's AI panel shows the run, usage and caps, stored assessment, and links to hypotheses and other agent outputs. Hypotheses, sessions, tool calls, findings and notes use bounded pages with visible remaining counts. Agent findings are unconfirmed and keep their stored lane. Only a lead with a valid CSRF token can request a new assessment; unfinished detection or a live agent lease refuses it.

Finding pages use an indexed importance order: lane, descending priority, observation time, then identifier. Validated opaque cursors preserve that order across pages, with null priorities and times last at their respective sort positions. Legacy hunt pages retain their original presentation.

Live activity reads an append-only sequence of committed substantive row changes, including in-place hypothesis, session and finding revisions; lease heartbeats do not add rows. A live page captures its starting sequence before reading findings, so its stream delivers only subsequent changes. Completed hunts and agent runs without a live lease do not open a browser stream; lease expiry affects stream eligibility only. Explicit API clients may request historical catch-up from sequence zero. Each page reads at most 200 changes and resolves current rows in bulk, with database work off the event loop. Full pages drain immediately; counts and state are sent only on a short page or at the end. Once both phases are terminal for streaming, the stream captures its terminal sequence and drains through it before closing. Per-connection finding history is disk-backed, and the browser retains only the newest 50 activity entries.

Templates escape agent content and browser updates use text nodes. Citation links resolve through identifiers belonging to the hunt. The assessment checker keeps sentences supported only by telemetry flagged as instruction-shaped and labels them "cites only content flagged as possible prompt injection" in Markdown, web and DOCX output. The checker footer counts these labels. These advisory flags never suppress assessment sentences; existing citation and absence-claim checks still apply. Typed tools and admission constraints also apply to instructions that are encoded or not flagged.
