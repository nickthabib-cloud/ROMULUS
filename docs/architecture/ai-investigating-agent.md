# AI investigating agent

ROMULUS can run a bounded AI investigation after its deterministic hunt stages finish. The agent reads the persisted hunt dossier, proposes investigation hypotheses, uses typed read and pivot tools, and writes separately labelled notes, links, rule requests, and findings. It cannot remove or change deterministic findings, lanes, coverage, incidents, or rule outcomes.

## Run flow

The hunt manifest records whether the agent was requested and which provider configuration was used. Provider readiness is checked without blocking the deterministic hunt. An unrequested, unavailable, or failed agent phase is recorded as skipped or partial and receives a deterministic template assessment.

Detection completion is recorded before agent work begins. The agent holds a separate renewable lease, including during blocking model calls. Its work cannot change detection execution state, and a live agent lease prevents deletion and maintenance. After agent work, one transaction refreshes the result from deterministic findings, records the agent's terminal state, and releases its lease. A crashed worker's persisted work can be resumed after lease expiry.

Assessment-only recovery closes a crashed investigation's running sessions under the newly claimed lease, records the interruption, and leaves the investigation partial even when the new assessment succeeds. The session cleanup and recovery audit commit together. A pending agent-off or unavailable-provider handoff can finish its template locally without contacting telemetry sources. Ready investigations still perform source preflight before resuming.

An orient session receives the system instructions and the first dossier page. It can open a bounded set of hypotheses. When there are reportable findings but no hypotheses were opened, the controller creates low-confidence hypotheses from the top finding in each incident.

The scheduler investigates open hypotheses in breadth-first rounds, with bounded concurrency and a per-hypothesis session limit. Each session starts a fresh conversation with the hypothesis card and a bounded set of earlier session summaries. Hypothesis updates and cites are persisted as events. The session stores its state, tool-call count, summary, and model calls so the phase can be resumed without rerunning a completed deterministic hunt.

After investigation, a schema-constrained assessment summarizes cited observations, inferences, hypotheses, gaps, alternatives, and next checks. The reply is validated against exactly the schema the model was given. A deterministic checker then removes uncited or unknown-alias sentences, downgrades observations supported only by AI or inferred links, blocks absence claims outside gaps and next checks, applies the stored bounds (sentence length, citations per sentence, sentences per section, each stated in the schema's descriptions), counts every sentence it drops or trims, and stores real identifiers in the report body. A reply that fails validation is retried once, with the failing fields named. A template based on the deterministic incident narrative and coverage gaps is used when no valid model assessment exists. A previous AI assessment is retained if a later attempt fails, and is labelled stale when investigation has changed since it was written.

## Admission and limits

All model actions use typed arguments. Each tool advertises the JSON schema of exactly the arguments its validator accepts: required and optional fields, defaults, bounds, patterns and enums, with descriptions for the rules a schema cannot state (which alias kind a field takes, registered rules, ATT&CK technique IDs, ordered windows). The tools that write (hypotheses, proposals, notes, rule requests and the session's end) ask the provider to enforce their shape where it can; read and pivot tools are validated by the product alone. A provider's strict mode can enforce only part of a schema and limits how much may be strict in one request, so the Claude adapter sends strict tools in a reduced form that states the other bounds in words, keeps within the documented limits and a conservative grammar budget, and sends the rest loose. Every call's arguments are validated by the product either way. When the session's wrap-up `finish_session` call is refused, the model gets one corrected attempt. Aliases are hunt-scoped, typed, and accepted only after they have appeared in trusted structured fields of the current session's prompt or a tool result. The claim checker restricts the claim kinds that each typed event family can support. Agent findings can be high or lead, and mention-only claims are lead. A duplicate proposal becomes a note only when the existing reportable finding has at least the admitted lane's strength. Duplicate checks stream matching candidates in bounded batches. Every output tool has a per-hunt cap; cap hits are recorded in the agent run. A refused tool call records why on its row as field paths and error types only (for example `summary: string_too_short` or `cites[]: alias_not_issued`), never the argument values, which can hold telemetry or model text; an assessment answer that fails validation records the same on its model-call row, the checker's drops as counts, and the triage pass its dropped items by field and reason. The agent's audit summary and the web panel show the refusals as counts by tool and reason.

Telemetry appears only in JSON data fields returned by tools. The system prompt treats it as untrusted input, and the provider port redacts outgoing text. The model cannot submit DSL, raw source queries, shell commands, paths, or SQL.

Budgets bound calls, tokens, wall time, and optionally cost. The token budgets count budget tokens, weighted by price: on the anthropic provider a prompt token read from the prompt cache counts `AGENT_CACHE_READ_TOKEN_WEIGHT` (by default 0.1) and one written to it `AGENT_CACHE_WRITE_TOKEN_WEIGHT` (by default 1.25) of an uncached one, output tokens count once, and every other provider counts each token once. The weights are recorded with the hunt's budgets, every call row records its budget tokens beside the raw counts, and the worst case checked before a call counts its whole prompt at the dearest weight. The controller preserves an assessment reserve during investigation, records billed provider failures, and checks remaining budget before retry attempts. An agent limit or provider failure affects the agent phase only.

Candidate citations have a transactional event index for duplicate checks and evidence lookups. Inserts and citation replacements maintain it in the same transaction; upgrades backfill existing candidates in bounded keyset batches. Incident construction projects only the stored provenance, ATT&CK and subject/context citation inputs it needs, preserving deterministic incident membership without loading full candidate rows.

## Reports

The manifest exposes agent provenance, usage, hypotheses, output counts, notes, rule requests, limits, and unworked hypotheses. Agent findings carry `provenance: "agent"`; agent links are displayed as hypotheses and do not join incidents. The Markdown report starts with the assessment and labels it as AI-generated and unconfirmed. The cross-hunt canonical projection keeps agent-only content in its `ai` section so it cannot alter deterministic comparisons.

Detection results and lane totals count deterministic findings, including genuine rule matches discovered by agent pivots. Agent-proposed findings are counted separately and labelled unconfirmed.

The CLI offers `hunt start --agent` and `hunt start --no-agent`, plus `agent reassess` to create another assessment revision and report revision. `--agent-model <id>` on `hunt start`, `hunt resume` and `doctor` replaces the configured model for that run only, and the manifest and agent run record the model used. A resume whose model differs from the one the hunt's agent recorded is refused unless `--force-model` is given.

The executive DOCX includes the same assessment header, sentences, citation labels and checker explanation as the manifest. Agent text is plain text in Word, including strings that resemble links or field instructions. Historical reports without an assessment retain their original rendering.

## AI triage order

After the agent phase ends, when the agent was requested and its provider is ready, a separate triage pass proposes which finding groups an analyst should review first. `romulus triage <hunt>` runs it on any finished hunt; `--export <file>` writes the resulting order as JSON (every surfaced finding id, in triage order) for evaluation. The pass claims the agent lease and always releases it without changing the agent's state; a hunt with no agent record is left with none, and an interrupted pass leaves only a terminal placeholder that every reader treats as no agent record and that is never resumed as an agent phase. `AGENT_TRIAGE=off` disables the automatic pass.

The deterministic report order stays authoritative. Triage changes no lane, rank, Reported flag, entity score, candidate, citation or report order: it is stored in its own table and rendered as its own labelled section, "AI triage order (model-proposed; the deterministic order is authoritative)", after the deterministic findings in the Markdown report, and on its own web page.

- **Groups, not the top of the ranking.** Every surfaced finding (urgent, high and lead lanes) is placed in a group: one rule on one primary target (the finding's listed entity from the final ranking, else its first typed host, service, address or account) within one report section. The model reads one card per group: rule and title, lanes, ATT&CK tactics, finding count, distinct entities with counts, time span, best deterministic position and up to three claim excerpts. Findings the AI agent proposed form their own groups and are never sent or promoted.
- **Untrusted card text.** Claims, entity names and every other telemetry-derived string are length-capped, carried as escaped JSON between data markers that the data cannot forge, and flagged when instruction-shaped. The system prompt treats them as data.
- **Validated output.** The model answers each card with a group id, an assessment (`likely_attack`, `possible_attack`, `likely_benign`, `insufficient_evidence`), an optional incident label clustering groups it believes belong together, a short rationale and up to eight finding ids cited from that card. Each item is checked on its own; an unknown or repeated group, a bad assessment, an over-long or malformed field or a citation from another group drops that item, counted by reason.
- **Promote-only, bounded in findings.** Within each report section at most `AGENT_TRIAGE_PROMOTE_PER_LANE` groups (default 10) assessed as likely or possible attack are promoted, the stronger assessment first, then by deterministic position; neither chunk order nor the model's own ordering decides. A promoted group moves ahead only the findings the model was shown for it, its claim excerpts (at most three, the only ones it could cite), group by group; the rest of the group and every other finding keep their deterministic relative order. No finding moves down by more than promote-per-lane x 3 findings (30 by default), and none is removed. The view lists each promoted group's moved findings and how many more stay in their deterministic place.
- **Budgets and honest partials.** Calls, prompt tokens, output tokens and wall time have their own settings; each call is checked first against its worst case, including the provider's thinking allowance. Cards are sent in chunks sized to one call's input and output room. A budget hit, a provider failure, a refusal or invalid output leaves the untriaged groups in deterministic order, and the view says how many groups were triaged and why the others were not. Triage calls are recorded as model calls and never spend the agent's budget.
- **Bounded and deterministic.** The deterministic order, groups and cards are staged in a temporary database under the stage directory, held to the site's stage byte budget and volume reserve (a refusal is a recorded failure that keeps the deterministic order), so memory is bounded by one page of findings and one card whatever the hunt's size. Cards are built once, for the digest and the calls. The view's rows are finished in the stage before publication, so the shared database's write transaction only inserts them. The pass's prompt digest covers the prompt, schema, grouping, provider, model, settings and every card: the same input gives the same order, and a completed pass with the same digest is not run again unless forced. The wall budget counts staging, and `AGENT_MAX_COST_USD` with the agent's prices caps each pass's cost when set. The report marks the view stale when the hunt's deterministic order no longer matches the pass's: it checks the finding count and final ranking, then digests the findings it already holds by the same order key the pass staged them by, without staging anything; a check that cannot run leaves the view unverified and never blocks the report. The web page uses the count and ranking checks. `romulus triage --export` re-stages the order, refuses a stale pass unless `--allow-stale`, and names the latest failed attempt. The stage keeps SQLite's temporary structures in memory and needs no large one: every index exists before its table is filled, and the order and groups are read through them. Findings an investigator case discovered stay in their groups and are counted on the card and in the view.

## Analyst views

The new-hunt form shows provider readiness and the configured model. Its agent checkbox follows the default only when the provider is ready, and any remote-egress banner appears before submission. The hunt's AI panel shows the run, usage and caps, stored assessment, and links to hypotheses and other agent outputs. Hypotheses, sessions, tool calls, findings and notes use bounded pages with visible remaining counts. Agent findings are unconfirmed and keep their stored lane. Only a lead with a valid CSRF token can request a new assessment; unfinished detection or a live agent lease refuses it.

Finding pages use an indexed importance order: lane, descending priority, observation time, then identifier. Validated opaque cursors preserve that order across pages, with null priorities and times last at their respective sort positions. Legacy hunt pages retain their original presentation.

Live activity reads an append-only sequence of committed substantive row changes, including in-place hypothesis, session and finding revisions; lease heartbeats do not add rows. A live page captures its starting sequence before reading findings, so its stream delivers only subsequent changes. Completed hunts and agent runs without a live lease do not open a browser stream; lease expiry affects stream eligibility only. Explicit API clients may request historical catch-up from sequence zero. Each page reads at most 200 changes and resolves current rows in bulk, with database work off the event loop. Full pages drain immediately; counts and state are sent only on a short page or at the end. Once both phases are terminal for streaming, the stream captures its terminal sequence and drains through it before closing. Per-connection finding history is disk-backed, and the browser retains only the newest 50 activity entries.

Templates escape agent content and browser updates use text nodes. Citation links resolve through identifiers belonging to the hunt. The assessment checker keeps sentences supported only by telemetry flagged as instruction-shaped and labels them "cites only content flagged as possible prompt injection" in Markdown, web and DOCX output. The checker footer counts these labels. These advisory flags never suppress assessment sentences; existing citation and absence-claim checks still apply. Typed tools and admission constraints also apply to instructions that are encoded or not flagged.
