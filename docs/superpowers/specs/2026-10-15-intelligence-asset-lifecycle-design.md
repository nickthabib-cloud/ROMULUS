# ROMULUS Intelligence Asset Lifecycle Design

## Purpose

ROMULUS must not retain intelligence files merely because they were researched or generated. Every retained asset needs one authoritative owner and at least one explicit consumer: runtime execution, build generation, operator documentation, or reproducible provenance. Duplicate and orphaned artifacts must be removed.

This design accompanies the source-aware execution design. It governs ownership, generation, reference enrichment, status reporting, documentation, and deletion.

## Asset classes

Every intelligence asset is classified as exactly one of:

- `authoritative_input`: edited source data used to generate or validate other assets.
- `generated_runtime`: reproducible output loaded by ROMULUS.
- `runtime_configuration`: operator-maintained data read directly by ROMULUS.
- `operator_document`: human-readable material linked from the project documentation.
- `historical_design`: an approved specification or plan retained as engineering history.

An asset with no valid class, owner, consumer, or regeneration path is orphaned and must be deleted.

## Authoritative ownership

- `docs/research/common-indicator-corpus.json` owns the 902 curated behavior records and 1,216 LOLBAS/GTFOBins capability references.
- `romulus/intelligence/attack_catalog.json` owns ATT&CK technique, detection strategy, analytic, data-component, and mutable-element data.
- `romulus/intelligence/behavior_catalog.json`, `windows_event_catalog.json`, and `search_matrix_catalog.json` own their compatibility, Windows-event, and Elasticsearch-matrix rules until migration into the common typed rule model is complete.
- `romulus/intelligence/local_indicators.json` is operator-managed runtime configuration.
- `scripts/behavior_pack_translations.json` owns reviewed transformations from research concepts to executable rule semantics.

Generated files never become an independent source of truth.

## Generated packs

The pack generator produces:

- `direct.json`
- `sequences.json`
- `aggregates.json`
- `baselines.json`
- `capabilities.json`
- `manifest.json`

`capabilities.json` contains the 1,216 LOLBAS and GTFOBins reference records only. ATT&CK analytics are not copied into a behavior pack because they remain available from `attack_catalog.json`.

The manifest separately reports executable, observe, reference-only, and unsupported counts. A loaded file is not described as executed coverage.

## Reference consumers

### Capability references

Capability references are indexed by normalized executable name. After deterministic candidate creation, ROMULUS may attach bounded reference context when cited evidence contains that executable. Context includes the published capability, URL, function, relevant follow-up, and source ID.

Capability context:

- cannot create a candidate;
- cannot add priority points;
- cannot satisfy corroboration;
- cannot become a finding;
- is bounded per candidate and deduplicated;
- records which evidence caused the lookup.

### ATT&CK references

Directed planning uses bounded `reference_seeds()` from the pinned ATT&CK catalog. Matching references enrich deterministic hypotheses and are included in model reasoning context after telemetry is collected. Unimplemented ATT&CK analytics appear as planning or translation gaps; they are not executed searches.

The unused model-only hypothesis planner is removed unless the runtime explicitly calls it under the existing evidence-first policy.

## Operator documents

`docs/research/README.md` is the inventory for all retained research assets. Each row records class, owner, consumer, regeneration method, and status.

Retained operator documents:

- `common-indicator-research.md`: research method, conclusions, provenance, and limitations. Repeated full indicator tables are removed.
- `indicator-priority-inventory.md`: the requested plain-language list of behavior names and priorities. It is generated from authoritative data and current pack state.
- `elasticsearch-dsl-search-matrix.md`: design and maintenance notes for the Elasticsearch matrix catalog.
- `windows-event-log-threat-hunting.md`: source research for the Windows event catalog and correlation work.

The main README links to the research inventory and operator priority list.

## Deletions

- Delete `docs/research/common-indicator-index.csv`; it duplicates the corpus, has no consumer, and has no distinct operator role.
- Delete the copied ATT&CK analytic index from the generated reference pack.
- Delete the obsolete `references.json` after `capabilities.json` replaces it.
- Remove stale generated bytecode and plan-owned temporary output only when it is ignored and not user data.

## Status semantics

Runtime and reports use these terms:

- `executable`: complete source-native retrieval and evaluation semantics exist.
- `executed`: all required stages ran successfully in the hunt window.
- `observed`: executable logic matched evidence but cannot independently escalate.
- `reference_only`: available for bounded enrichment or planning, never evaluated as a detection.
- `unsupported`: intended executable behavior lacks complete semantics.
- `not_applicable`: required telemetry or fields are unavailable.
- `omitted_budget`: executable work was not scheduled because of a recorded resource limit.
- `partial`: source errors, caps, missing stages, or truncated state prevent a complete conclusion.

`loaded` may describe file integrity only and cannot substitute for any execution state.

## Reproducible audit

Add an offline intelligence-asset auditor that checks:

- every declared asset exists;
- every retained asset has a valid class, owner, and consumer;
- every generated asset is listed in the manifest and matches its hash;
- no generated ATT&CK analytic copy exists;
- no retired asset is referenced by code or documentation;
- corpus and pack counts reconcile;
- status labels do not claim execution for inert rules;
- operator documents name their authoritative source and regeneration method.

The audit fails closed and emits a compact machine-readable summary.

## Secondary project audit

After implementation, perform a fresh repository-wide audit covering:

- orphaned modules, functions, data, and documentation;
- duplicate sources of truth;
- generated files edited independently of their generator;
- mismatched source query languages;
- unreachable code and unused public interfaces;
- status or count fields that overstate behavior;
- stale documentation and contradictory claims;
- temporary, cache, credential, report, or telemetry artifacts that could enter a commit;
- unusually large files without a declared consumer;
- error handling that silently converts failure into no-match coverage.

Findings are corrected when within the approved intelligence architecture. Unrelated product behavior is documented for separate review rather than changed opportunistically.

## Acceptance criteria

- The CSV duplicate and ATT&CK reference-pack copy are absent.
- `capabilities.json` contains exactly 1,216 capability records and has a bounded runtime consumer.
- `attack_catalog.json` contributes bounded references to planning and reasoning.
- Sequence, aggregate, and baseline content is either executable through the source-aware design or explicitly unsupported/reference-only; counts alone are not called usage.
- The priority inventory is generated from authoritative current data.
- Research files are indexed and linked.
- The offline asset audit passes.
- The secondary audit reports the whole repository scope, findings corrected, and any remaining limitations.
