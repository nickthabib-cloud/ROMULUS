# Network protocol contracts

Typed field origins name the source record and native field. Missing values remain missing. A recognized malformed application subrecord rejects its enclosing EVE record atomically and is counted as a normalization error. A protocol that is not implemented is counted as not normalized.

`detect.network_producers.protocol_record(event, family)` checks the exact family and a known producer identity. It does not prove that a particular record contains every field a rule needs. Rules must retain their field, outcome, identity and coverage checks. The helper accepts Zeek and Suricata protocol contracts; it excludes Arkime's unordered session sets from transaction rules.

`rule_reads(event, producers)` is the gate each network rule applies. The RPC administration, coercion and replication rules, the WinRM rule, the RDP rules and the Netlogon, NTLM and RPC enumeration rates read Zeek and Suricata records, since each needs only facts both sensors type alike. An RPC call is identified by endpoint and operation names or by interface UUID and opnum; Suricata records the interface beside the opnum for calls over SMB named pipes, and a standalone DCERPC request record carries only the opnum, so its call is not classified and these rules do not judge it. HTTP and SMB records are in their flow's direction. Suricata writes each RDP message in its packet's direction, so the RDP rules judge only its client's `initial_request` (`rdp.message`), once per connection. An NTLM outcome is typed from the session setup's own status (success, or a listed logon failure) and is otherwise unset, which the rates count as an attempt, as for Zeek. The other network rules read Zeek only: the Kerberos rates (Suricata's request, reply and error records are not typed apart, so a rate would count one exchange more than once), the requested-ticket-lifetime rule (Suricata does not record the requested till), the VNC rule (Suricata RFB records are not normalized) and the SMB admin-share executable rule (Suricata gives no cross-record file identity and direction). A rate that counts raw references keeps its count per sensor, so two sensors on one link do not double it; a rate that counts distinct members shares them across sensors.

Common available network fields are `source.ip`, `source.port`, `destination.ip`, `destination.port`, `network.transport` and `network.community_id`, when carried by the record. Suricata also preserves `suricata.flow_id`. These are sensor observations, not endpoint execution records.

### Suricata interpretation limits

A request/response transaction is one event. An SMB authentication or RPC subrecord gets its own typed family and identity with the enclosing raw reference. Candidate RPC interfaces are not multiplied into calls; multiple unpaired interface candidates leave classification unresolved.

SMB uses flow orientation in [Suricata's SMB logger](https://github.com/OISF/suricata/blob/suricata-8.0.0/src/output-json-smb.c#L68). Its [transaction serializer](https://github.com/OISF/suricata/blob/suricata-8.0.0/rust/src/smb/log.rs#L131) supplies the same SESSION_SETUP record's status and NTLM child. `STATUS_SUCCESS` means success; the explicit logon/account failure statuses in [MS-ERREF](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-erref/596a1078-e883-4972-9bbc-49e60bebca55) mean failure. More-processing, unrelated commands, other statuses and missing status remain unknown. An SMB2 CREATE or SET_INFO with `access: delete on close` supplies `FILE_DELETE` as a requested operation, not proof of completed deletion. The disposition information-class name alone does not establish deletion.

RDP and Kerberos use packet direction ([KRB5 registration](https://github.com/OISF/suricata/blob/suricata-8.0.0/src/output.c#L1176), [RDP registration](https://github.com/OISF/suricata/blob/suricata-8.0.0/src/output.c#L1231), [tuple construction](https://github.com/OISF/suricata/blob/suricata-8.0.0/src/output-json.c#L492)). Their source/destination tuple is preserved as written, so a server response can have the server as source. RDP clients send `initial_request` and `connect_request`; server-side records include `initial_response`, `connect_response` and `tls_handshake` ([parser](https://github.com/OISF/suricata/blob/suricata-8.0.0/rust/src/rdp/rdp.rs#L211)). All five values become `rdp.message`. Kerberos client/KDC fields use the unique port-88 end for TCP or UDP. Neither or both ends on port 88 leaves these roles unset with a caveat. Non-standard KDC ports are not inferred.

Kerberos `ticket_encryption` on an AS/TGS reply is the issued ticket's encryption type. EVE `encryption` describes a different encrypted part and is not substituted for it; an unknown value adds a caveat without discarding valid ticket facts. Unknown ticket-cipher names remain normalization errors. Names map to numeric etypes through the shared IANA/RFC table; [RFC 3961](https://www.rfc-editor.org/rfc/rfc3961), [RFC 4120](https://www.rfc-editor.org/rfc/rfc4120) and [RFC 8009](https://www.rfc-editor.org/rfc/rfc8009) describe the algorithms and identifiers. KDC error attribution requires the failed AS/TGS request indication. Missing ticket cipher or error attribution cannot support the corresponding credential rule.

Suricata's `cname` is the principal without an appended realm ([serializer](https://github.com/OISF/suricata/blob/suricata-8.0.0/rust/src/krb/log.rs#L42), [principal formatter](https://github.com/rusticata/kerberos-parser/blob/kerberos-parser-0.8.0/src/krb5.rs#L37)); it becomes `kerberos.client_name` unchanged. Zeek's `kerberos.client` includes its final `/REALM`, which the Zeek adapter already separates into `kerberos.client_name` and `kerberos.client_realm`. A realm is not invented from Suricata's separately emitted service realm.

The Suricata 8 LDAP serializer emits only presence filters. Other LDAP filter forms that it does not serialize stay unknown; no filter or entry count is reconstructed from absent data. RDP client product ID comes from the serializer's client `id` field.

`anomaly`, `quic`, `http2`, `sip`, `mqtt`, `ike`, `pgsql`, `nfs` and `rfb` remain counted as not normalized: their current EVE layouts have no implemented direct correspondence to the required typed contracts. No unsupported record becomes a clean negative.

Format and field semantics follow the [Suricata 8 EVE reference](https://docs.suricata.io/en/suricata-8.0.0/output/eve/eve-json-format.html) and its [protocol serializers](https://github.com/OISF/suricata/tree/suricata-8.0.0/rust/src).

## SMB impact observations

`network.smb_impact` folds by client, server and share within a closed five-minute window:

- At least 100 distinct extension-changing destination names with at least 80% sharing one new extension: high lane, critical severity, T1486 context.
- At least 200 distinct renamed/deleted names: lead lane, high severity.
- Exact whole names or bounded anchored forms from `content/network/ransom_notes.json` opened or created in at least 10 directories: lead lane, high severity. Repeated opens in one directory count once. Generic readmes are excluded; case folding preserves Unicode lookalike differences. Names alone do not prove file contents, and incident-response copies remain possible.

Native Suricata 8 rename records do not themselves carry the share path: the serializer emits it on other SMB operation types. This rule does not join tree/session IDs across records. A rename without independently supplied share context is unresolved for this rule; the enriched Suricata fixture proves the typed integration only. Zeek SMB file records already supply the share path.

Counts are distinct canonical names, not actions. Missing previous names support only the volume arm. Final-extension or trailing-tilde removal, same-stem temporary-to-document/image completion, and the narrow Word save-via-temp pattern are volume-only. The completion suffix set is `.pdf`, `.tif`, `.tiff`, `.jpg`, `.jpeg`, `.png`; this covers scanner `.part` to `.pdf` completion without exempting `.tmp` to `.locked`. Changed extensionless names are volume-only with unresolved encryption status. Arbitrary uniform victim-specific extensions remain eligible. Late records replay from bounded disk history before the ratio is published.

Completeness is tracked per client/server/share on disk. A refusal for another group or loss of extra citations does not invalidate retained members. An incomplete group with at least 100 retained names changed to one extension remains high with an explicit lower-bound claim and unresolved ratio; the 80% ratio is asserted only for complete groups. If refusal bookkeeping cannot be retained or safely recovered, all groups become conservatively incomplete. Known positives remain reportable; incomplete below-threshold groups contribute honest limits.

## Service-name observations

`network.service_catalog` reads typed singular/plural DNS question names, TLS SNI and HTTP Host. Host ports are removed; bare IP hosts do not match. It uses case folding, an ASCII fast path, IDNA for non-ASCII/punycode names and exact or label-boundary suffix matching through a reversed-label trie. DNS syntax is required for consumed suffix labels; opaque labels to their left may contain underscores. Empty labels and overlong names are malformed. At most 1,024 names per record are evaluated, with an explicit partial-membership limit when capped. URI parameters, body text and TXT answers are not name keys.

`content/network/services.json` records each entry's suffixes, category, techniques, sources and licensing basis. Remote-access, tunnel and IDE entries are high severity; callback and file-sharing entries are medium. Every observation remains a lead. Claims describe a lookup or connection, never that software ran or transferred data.

The catalog includes ngrok agent control and regional tunnel names, MEGA API/storage, DNSLog/Ceye callbacks and sourced Pastebin/Paste.ee/Hastebin observations. GoTo coverage uses remote-support domains and excludes shared `logmein.com`/`logmeininc.com` collaboration infrastructure. It is an original factual compilation; no upstream catalog or prose is copied. DNSLog/Ceye entries cite Knownsec/FullHunt references.

Source groups fold by entry and internal address; fleet summaries stream membership and count distinct addresses. NAT and resolvers can hide multiple machines. Final rule output puts entries seen at one or two sources first; overall report ranking remains governed by the report policy.

The optional `approved_remote_access` list in `site/collection.yaml` accepts service catalog IDs or exact DNS suffixes. An ID covers its whole entry; a suffix covers that entry only within that label-boundary suffix and does not approve sibling suffixes. Approved observations produce one fleet lead, including a one-host fleet; unapproved observations retain per-source leads. Fleet membership streams with exact counts while event citations contain at most two witnesses; citation and retention shortfalls are explicit. A known approved positive retains a partial fleet lead if optional group state cannot be kept. Omission preserves the previous site-fact digest.

## HTTP attack observations

`network.web_attacks` uses one rule with seven explicit classes: SQL injection, cross-site scripting, path traversal/local-file inclusion (including requests for sensitive files), remote-file inclusion, OS command injection, server-side template or expression injection, and known exploit, scanning and brute-force tool user agents. Sharing the bounded decoding pass and disk fold avoids seven copies of the same request. Each class retains its own finding identity and count. A second rule, `network.web_login_burst`, uses the existing disk-backed transaction-window engine.

| Typed fact | Zeek HTTP | Suricata HTTP | Arkime session |
|---|---|---|---|
| Request target | `uri` → `url.original` | `http.url` → `url.original` | `http.uri` → unordered, host-prefixed `url.path` list |
| Method | `method` → scalar `http.request.method` | `http.http_method` → scalar `http.request.method` | Unordered `http.request.method` list; not paired |
| Response status | `status_code` → scalar `http.response.status_code` | `http.status` → scalar `http.response.status_code` | Unordered status list; not paired |

| Requested host | `host` → `http.hostname` | `http.hostname` → `http.hostname` | `http.host` → `http.hostname` list |

`rule_reads` admits only explicitly declared producers. The Arkime observation path does not change `protocol_record`'s transaction exclusion. A session containing an attack URI is a session-level observation; its status and user-agent lists cannot establish that the attack request received a particular response.

### Decoding and bounds

Request targets and user agents undergo plus-to-space conversion, at most two percent-decoding passes, HTML entity decoding and case folding. Decoding never refuses a value:

- A `%` that does not start an escape is a literal.
- `%uXXXX` is read as its code point.
- Bytes that are not UTF-8 are replaced, the grammars still run, and the record is counted as partly inspected (`utf8`).
- UTF-8 forms longer than the shortest one for their character are read as that character. An overlong-encoded `/`, `.` or `\` is itself reported as path traversal: no client produces one except to pass a filter.
- A third level of percent-encoding is not decoded.

The first 16,384 characters of a request target and the first 2,048 of a user agent are inspected; a longer value is read up to that bound and the record is counted as partly inspected (`length`). Every value of an Arkime list is inspected, in order, until the record's 65,536-character budget is spent; a repeated value costs one character. When the budget runs out the remaining values are not read and the record is counted as partly inspected (`text`). Known positive values in a partly inspected record remain reportable, and their finding says how many of its records were partly inspected. No body, serialized document or arbitrary message field is searched.

### Grammars

Each pattern requires the structure of an attack, not a keyword:

- **SQL injection:** `UNION SELECT` followed by an operand (a number, `*`, `NULL`, a quoted literal, or a column or function name followed by `,`, `(` or `FROM`); a statement after a closing quote or `;`, where each verb needs the words that make it a statement (`INSERT INTO`, `UPDATE x SET`, `DELETE FROM`, `DROP TABLE x`); a boolean clause after a closing quote; a numeric tautology (`1 or 1=1`, both numbers equal); a quote followed by a comment that ends the value (`admin'--`); `ORDER BY n` column counting; `WAITFOR DELAY`; `information_schema.<table>`; `extractvalue(`/`updatexml(`; `xp_cmdshell`; and timing calls that are closed and followed by SQL. A MySQL versioned comment (`/*!50000union*/`) keeps its body; a plain comment is removed.
- **Cross-site scripting:** a `<script` tag; an event-handler attribute on any element, or after an attribute value that was closed early; `javascript:` followed by a dialog or `eval` call.
- **Path traversal and local files:** a request path that steps above its root; a parameter value that climbs three or more levels, or climbs at all and ends at a configuration, hidden, log, key or backup file; operating-system files (`/etc/passwd`, `boot.ini`, `win.ini` and similar); environment, repository and key files (`/.env`, `/.git/config`, `/.htpasswd`); stream wrappers given as a parameter value (`php://filter`, `expect://`, `file://`); `/..;/` and `....//` spellings; and overlong-encoded separators. A NUL after a file name ends the name.
- **Remote-file inclusion:** a remote URL (with a scheme, or scheme-relative with a dotted or address host) in a parameter named after the include statement (`include`, `require`, `inc`); or in a file-like parameter (`page`, `file`, `path`, `template`, `doc`, `document`, `root`) when the URL has an IP-literal host, ends with `?` or a NUL, or ends in `.txt`, `.inc`, `.dat` or `.tmp` (an include payload has to reach the server as source text, so it is often served under an extension the attacker's own server does not execute). A URL in a file-like parameter that ends in a script extension (`.php`, `.phtml`, `.asp`, `.aspx`, `.jsp`, `.cgi`, `.pl`), with or without a query of its own, is reported when both hold: the request goes to one of the site's own servers (its destination is inside the site's internal networks), and the URL's registered domain differs from the requested host's, or no host was recorded, or the host is an address. A page URL carried outward to a third-party collector, and a site's own tools naming the site's own hosts, therefore do not match. A URL whose host is the requested server itself (the recorded `Host`, or the destination address) is not remote in any of these forms; its path is still read by the local-file grammar. Redirect parameters (`next`, `url`, `redirect_uri`) are never inclusion.
- **Command injection:** a shell separator followed by a command from a stated list with an operand (a flag, a path, a number, a quoted word, a redirect or a URL); a command that is unambiguous on its own (`whoami`, `uname`, `ipconfig`); a command that needs no operand directly after a complete value (`127.0.0.1;id`, `127.0.0.1|dir`); a decoded `&` that begins a command with an operand; `$(command)`; `` value`command` ``; and the Shellshock function prefix.
- **Template and expression injection:** template delimiters (`{{ }}`, `${ }`, `#{ }`, `<% %>`) containing multiplication or addition of literals, double-underscore attribute access or a framework object; `{{config}}`; a JNDI lookup (`${jndi:`) or a lookup nested to hide one; Java runtime execution expressions.
- **Tool user agents:** identifiers of sqlmap, Nikto, commix, Nuclei, Nmap Scripting Engine, WPScan, WhatWeb, Recon-ng, Nessus, OpenVAS, Acunetix, w3af, Arachni, ZAP, Havij, sqlninja, DotDotPwn, ZmEu, Morfeus, Webshag, Grendel-Scan and Vega (vulnerability scanning); gobuster, DirBuster, dirb, Wfuzz, ffuf and feroxbuster (wordlist scanning); masscan and zgrab (address-block scanning); Hydra and Medusa (password guessing). A marker is a whole token of the user agent, the finding names the markers it saw, and its ATT&CK context is the technique of what the tool does. The injection grammars also read the user agent, where only an explicit operand or substitution counts as a command.

What does not match: isolated SQL words and prose that contains them (`union select tutorial`, `"select committee"`, `'insert coin'`); URL-encoded JSON interface strings (`"Select a country"`, `"Update profile"`); base64 and tokens; delimiter lists (`fields=name;id`, `cols=name|id|date`, `titles=Dog|Cat|Bird`); markdown inline code that follows a space; relative references one or two levels up (`next=../home`, `src=../uploads/a.jpg`) and in-root navigation; unexpanded placeholders, dates and ranges (`{{customer_name}}`, `{{2024-01-15}}`, `${start}-${end}`); ordinary tracking parameters; and client libraries such as `python-requests`, `curl` and `Go-http-client`.

What still matches without being an attack: authorized testing; search text or a document that holds a complete payload (`1 or 1=1`, a `UNION SELECT` with a column list); a page editor that carries HTML with event handlers; markdown inline code that directly follows `=` or a word; a delimiter list whose item follows a number and is a command name; an application that includes remote text files by design, or that one of the site's servers is asked to fetch from another domain by design; and arithmetic on literals in an unexpanded placeholder. What is missed: a bare ambiguous command after a word (`host=localhost;id`), a remote script URL in a request to a server outside the internal networks, a remote image or extension-less URL without a trailing `?`, encrypted traffic, novel grammars and attacks visible only in request bodies. The rule is positive-only.

### Findings and roll-ups

Observations fold by source address, destination address and class. Canonical event identities are counted once on disk, independently of the retained example citations; distinct inspected values after decoding/case folding and Arkime sessions are counted separately. These exact retained-observation counts do not claim distinct network requests across sensors or re-indexes.

Each class is reported per pair of source and destination. Once an endpoint has more than five pairs for a class, the five with the earliest first record (then the lower address) keep a lead of their own and the class against that endpoint is reported once:

- one **fleet** lead per destination and class, whose members are the sources;
- one **sweep** lead per source and class, whose members are the destinations.

A roll-up carries the exact number of distinct members, the ten members with the most observations in its claim and as address entities, two records of the group as citations, and the complete member list as a streamed list. Members on different sides of the site boundary are separate roll-ups. Outside addresses are listed as outside addresses and never join the hunt's host population. Internal addresses are listed as internal addresses; the evidence ranking resolves each to the host whose own telemetry carries that address (or keeps the address when no host does), gives that host the finding's tactics, and counts it once in the host population, so a server reached only through a roll-up carries the same evidence as one named in a lead of its own. When exactly one endpoint is internal, the roll-up anchored on the internal endpoint is always published, and the roll-up anchored on the outside endpoint is published only for a pair the first one does not cover; so the number of findings follows the site's own addresses, not the number of outside addresses taking part. Every pair is covered by its own lead or by a roll-up, and roll-ups stay in the lead lane. Under the default internal ranges the side of an address is an assumption, and the finding says so.

Which pairs keep a lead and which roll-ups stand is decided from the times of first records, so the same records give the same findings in whatever order they are read. Records read in time order are published, as they arrive, as exactly those findings. When records arrive out of time order (a second sensor read later), a pair can have a lead published on arrival that does not stand at the end: it keeps that publication, worded as a lower bound, and at most fifty such leads are published per endpoint and class; and a roll-up anchored on an outside address that only the later records make necessary is published when the sweep finishes.

A disk refusal preserves the live positive: each pair is reported once while the state cannot grow (up to 4,096 pairs, then once per class), coverage counts every record that was not folded, and from then on counts are stated as lower bounds.

All classes remain **lead**, including a tool marker with a 2xx response. Neither a response status nor response size establishes exploit execution. Site-declared management sources, given as addresses or networks, receive an authorization note and retain their lane. User-agent markers are spoofable and configurable; a named tool may use an ordinary browser identifier.

### Credential masking in retained examples

A cited request target is masked before it is stored. A query or path parameter loses its value when its name has a credential word as one of its parts: `pass`/`passw`/`password`/`passwd`, `pwd`, `pw`, `secret`, `token`, `key`, `sig`/`signature`, `sess`/`session`, `sid`, `auth`/`authorization`, `cred`/`credential`, `otp`, `pin`, `code`, `jwt`, `bearer`, `csrf`/`xsrf`, `cookie`, `ticket`, `assertion`, `saml...`, and compounds written without a separator such as `apikey`, `secretkey`, `userpass`, `sessionid` and `PHPSESSID`. Names are split at every character that is not a letter or digit, at lower-to-upper case changes and between letters and digits, and are also read as one word across those splits, so `user[password]`, `txtPassword`, `X-Amz-Signature`, `password1`, `pAsSwOrD` and `pass_word` are recognised and `monkey`, `author`, `compass` and `passenger` are not. Names in other languages (`kennwort`, `contrasena`, `senha`) and short or ambiguous ones (`p`, `k`, `state`, `hash`) are not recognised. A query parameter ends only at `&`: a `;`, `?` or `#` inside it may belong to the credential's value, so the whole value goes. The rest of the request stays readable. When an encoded delimiter or an HTML entity makes the end of a credential's value ambiguous, the whole query is omitted instead. In the path, a credential piece (`;jsessionid=...`, or `name=value` written into a segment) is masked to the end of its segment, and through a following `?` or `#` when the text after it names no parameter; a credential name that only appears once the kept text is decoded withholds the whole target. URI userinfo is removed wherever a URL appears, and a value longer than 2,048 characters is truncated. A secret under a name outside this vocabulary, or written into the path itself, is not recognised and is retained. Native references remain; producer raw-evidence handling is unchanged.

### Login bursts

The login rule observes at least **20 request raw references in a closed five-minute window**, grouped by source, destination, path and sensor. One person typing credentials submits a few times a minute, and account-lockout settings stop one account well short of twenty failures, so twenty is beyond a person's retries while any guessing tool passes it within seconds. Many users behind one address (NAT, a proxy, a sign-on portal) can also reach it, so the claim states the response-status mix of the peak window (for example "28 answered 302, 2 answered 200") and the lane stays lead.

A request is counted when:

- its path has a sign-in segment (`login`, `logon`, `signin`, `signon`, `sso`, `auth`, `authenticate`, `token`, `session`, `logincheck`, `j_security_check`, `wp-login.php`, `xmlrpc.php`, `auth.owa`, `administrator`, `phpmyadmin`) and it is a POST with a recorded response of any status, or any request answered 401, 403 or 429, or a request whose query carries an account and a credential parameter; or
- on any other path, its query carries both an account parameter (`user`, `username`, `login`, `email`, `account`, `log`, `j_username`, `uname`, `userid`) and a password parameter (`password`, `passwd`, `pwd`, `pass`, `pw`, `j_password`), and the window holds at least two distinct credential pairs.

The second arm counts distinct pairs because a device or a service that polls with its own fixed credentials (a recorder fetching camera snapshots, a gateway API) repeats one pair, while guessing and spraying do not. Pairs and account labels are compared by a keyed hash whose random key lives only in the running rule and is never stored, so a stored label cannot be tested against a guessed password; a resumed hunt reads its records again under a new key. The claim states the number of distinct pairs. Several users or devices behind one address that each send their own credentials also give several pairs.

A sign-in path also serves session heartbeats, token refreshes and an administrator's work in a console. The claim therefore says "requests to a sign-in path" and states what is recorded (the requests and their statuses) and what is not (that each was a login attempt, and any login's outcome).

A path parameter such as `;jsessionid=` is not part of the path. Ordinary GET form retrievals (including a username alone), POSTs to other paths, and Arkime lists do not count. A request with no recorded response is counted as missing a required field, not as a non-match. Account labels use one ordinary form-decoding pass without case folding or HTML interpretation, independently of attack-grammar decoding. Late records replay from disk, repeated/known account labels count exactly, and absent accounts share an explicitly unknown bucket. No status is treated as authentication success or failure. Guessing slower than the threshold, spread over many sources, or visible only as failure statuses on other paths is not counted.
